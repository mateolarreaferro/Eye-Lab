# Vision Quest (VR)

A small Godot XR game built on the `godot-xr-template` (VRatMIT), for the
"Make a vision game" assignment. Where the desktop Eye Lab app applies its
spatial-frequency filter to the whole screen for both eyes, this applies it
**dichoptically** — differently per eye — which only a stereo headset can do.

## The idea

"Perceive More By Seeing Less" (and the dichoptic-rebalancing literature it
sits alongside) proposes that amblyopia treatment doesn't need to fully patch
the strong eye. Degrading the strong eye's contrast/low-frequency content by
just the right amount forces the visual system to recruit the weak eye,
while keeping both eyes open so binocular fusion cues survive. A monitor
can't target one eye without the other, but a VR headset renders each eye
separately, so it's a natural place to actually build this.

`shaders/dichoptic_filter.gdshader` is the same high-pass "frequency
patching" math as `eye_lab/shaders/filter.gdshader` (mode 1), gated by
Godot's `VIEW_INDEX` so it can render into just one eye's view. See
`scripts/dichoptic_filter.gd`.

**Two modes**, because amblyopia isn't always unilateral:
- **Dichoptic** (`filtered_eye` = Left/Right): the common case — one eye is
  measurably weaker than the other. Set this to the child's *dominant*
  (non-amblyopic) eye; filtering it stops that eye from dominating/
  suppressing the weak one. This only works when there's an asymmetry to
  correct.
- **Binocular** (`filtered_eye` = Both): for bilateral amblyopia, where
  neither eye dominates so there's nothing to rebalance against. Both eyes
  get the same filtered, harder-to-resolve view instead — general acuity/
  contrast training rather than interocular rebalancing, same idea as the
  desktop Eye Lab app's whole-screen filter.

Per-child mode should be set based on their actual diagnosis (which eye, if
either, is dominant) — this isn't something the game can infer on its own.

## The game

`scripts/vision_quest_game.gd`: the player is dropped at a random cell in
the city-maze; the objective is to spot and walk to a glowing beacon placed
at a *graph-distant* cell, using sight alone (no compass/waypoint arrow —
finding the beacon *is* the visual task, made harder by the filter).
"Graph-distant" is the important part: the target isn't just a random
point, it's picked via BFS over the maze's actual connectivity graph, so
every round has a genuinely long, winding solution path rather than an
occasionally-trivial random one. Reaching it starts a new round.
Locomotion is the template's stock joystick movement (`scripts/xr_move.gd`);
`scripts/player_wall_collision.gd` is a separate autoload that pushes the
player out of overlapping geometry each physics frame, since the template's
locomotion moves position directly with no physics query -- without it, the
maze walls wouldn't actually block anything.

## The city-maze

`environment/city.glb` + `environment/city_maze.json` are generated by
`tools/generate_city.py`, run headless through Blender, no manual modeling:

```sh
blender --background --python vr_game/tools/generate_city.py
```

- **Style**: a European canal-town look (steep gabled roofs via a small
  bmesh-built triangular-prism roof shape, warm stucco walls, cobblestone
  streets, a canal along the south edge) rather than a generic box grid.
  This was scoped down from a request to match Marble/Gaussian-splat-level
  photorealism -- that's a different rendering technology entirely (splats,
  not meshes) that doesn't support collision/maze-blocking, which is why
  this stayed mesh-based. See the conversation this was built from for the
  full reasoning.
- **Maze**: a recursive-backtracker carves a *perfect* maze (exactly one
  path between any two cells, real dead ends) over a 5x5 grid of city
  blocks. Where a passage between two adjacent blocks is "closed", a solid
  building fills that entire street gap, physically blocking it. The graph
  (which edges are open, plus each cell's world position) is exported to
  `city_maze.json` alongside the geometry so gameplay code can reason about
  difficulty, not just geometry.
- **Performance note**: the generator originally used `bpy.ops.mesh.*_add`
  in a loop, which is dramatically slow at this object count (it hung for
  minutes); it now builds geometry directly via `bmesh`, which is fast
  (~7s for the whole city). Per-building detail was also deliberately kept
  minimal (one window row, no shutters) since it repeats across ~190
  buildings -- more detail here is a direct cost to Quest draw-call count.
  Current output is ~1070 nodes/meshes, 1.4MB; untested on-headset for
  actual framerate, worth checking once you can.
- **Points of interest**: dense per-building detail (shop signs, lit
  "interior glow" windows) is only added to a curated subset -- buildings
  near the landmark and the fountain plaza -- rather than uniformly across
  all ~190 buildings, to keep it from repeating the earlier draw-call
  mistake. Two fountains (one by the landmark, one at a random 3+-way
  crossroads), planters, and benches follow the same "detail concentrated
  at points of interest" logic.
- **Memorable landmarks**: every maze dead-end (a cell with exactly one
  open passage) gets a unique building instead of the usual rowhouse row --
  a round tower, a visibly leaning house, a turret house, or a clocktower,
  picked in rotation. This isn't just decoration: a dead-end with a
  distinctive silhouette is a real wayfinding cue ("dead end was the
  leaning house") for a maze meant to be genuinely hard. How many of the
  4 types actually appear depends on how many dead-ends that maze layout
  happens to produce.
- **Scoped out**: real building interiors. Nothing in the game lets a
  player open a door or enter a building -- they're obstacles you navigate
  around, not spaces you enter -- so modeling actual rooms/furniture behind
  walls nobody can reach would be pure wasted geometry. The lit-window
  detail above gets the "lived-in" feel from outside instead, at near-zero
  cost.

Edit the constants/helper functions at the top of the script (grid size,
building dimensions, colors, maze seed) and re-run -- it overwrites both
output files in place. `vision_quest_game.gd` loads `city.glb` at runtime
and generates trimesh collision for every mesh (glTF imports have none by
default), and separately loads `city_maze.json` to run its BFS-based
spawn/target selection.

## Ambient life

`scripts/city_life.gd` (autoload): birds circling above the city, a
pulsing light atop the landmark, a handful of pedestrians and pets (small
wandering blobs, ellipsoid-squashed spheres) patrolling open street
segments. Purely cosmetic -- motion does more for a scene "feeling real"
than added geometric detail does, and it's cheap since it's plain runtime
GDScript rather than new geometry/pipeline.

## Status / what's not tested yet

Godot isn't installed on the machine this was scaffolded on, so **none of
this has been opened in the editor yet**. Before relying on it:

1. Open the project in Godot 4.7, confirm it loads `main.tscn` without
   errors.
2. Install the Godot OpenXR Vendors plugin (Asset Store, top bar) if it
   isn't already — same step as the base template.
3. Check the dichoptic quad's facing/depth in-editor (`depth_test_disabled`
   + `cull_disabled` should make orientation robust, but verify visually)
   and that VIEW_INDEX gating actually renders one eye only when run on
   headset or in the OpenXR mobile mirror.
4. Tune `lod`/`gain` on `DichopticFilter` — these were ported from the
   desktop app's defaults, not tuned for VR FOV.

Update, tested via Meta XR Simulator: the *previous* simpler version (open
grid city, random spawn/target, no collision) was confirmed working end to
end -- dichoptic per-eye filtering, locomotion, spawn/beacon win loop.

The maze/collision/ambient-life rebuild went through the simulator and was
confirmed working (per-eye filter, locomotion, spawn/beacon loop, view
rotation). The points-of-interest pass just above (fountains, landmark
buildings, signs, pets) has **not** been re-tested since it was added --
regenerate (`blender --background --python tools/generate_city.py`, already
done once here) and re-run in the simulator before trusting it's solid.
Specifically worth checking:
- The new landmark buildings/fountains don't clip into their block's
  regular rowhouses or block a passage they shouldn't
- Whether the added ~10 objects hold framerate alongside everything else
- Pets/pedestrians actually visible and moving along real open streets
